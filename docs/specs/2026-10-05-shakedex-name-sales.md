# Shakedex name sales

**Status:** accepted (2026-10-05); buying implemented; selling and the clean-up not yet. Supersedes [2026-09-21 Paid name swaps](./2026-09-21-paid-name-swaps.md). Decisions: [ADR 0003](../adr/0003-own-shakedex-implementation.md) (own implementation), [ADR 0004](../adr/0004-shakedex-lock-keys-from-seed.md) (lock keys from the seed). Delivered in three stages — buying, selling, and the clean-up that removes the withdrawn paid-swap code — see Pointers.

## 1. Summary

Selling a Handshake name for HNS should take one transaction that either pays the seller and commits the name to the buyer, or does neither. Shakedex does that, and the one live name market, LearnHNS Market, runs on it; Bob Wallet and the shakedex CLI speak the same listing file. Namehold can do neither today, so its users are locked out of the only live market. This spec makes Namehold a full Shakedex participant: browse and buy listings from LearnHNS Market or a listing file, and sell names as Buy Now listings or reverse auctions that any Shakedex-compatible wallet can buy. Everything a buyer relies on is checked locally, against the profile's node; the market is a convenience, never a source of trust.

## 2. Terms

Listing, Pending listing, Buy Now, Reverse auction, Price step, Current step, Listing file, Lock, Lock key, Purchase, Unconfirmed purchase, Awaiting finalize, Sold, Market fee, Cancel and Lower price are defined in [CONTEXT.md](../../CONTEXT.md) under "Name sales (Shakedex)". Shakedex's own words — auction, bid, presign, proof, fill — appear only at the protocol boundary (`noncustodial/shakedex/`, the `proof.json` URL), because in this wallet a bid is a buyer's sealed offer in a name auction, the opposite direction of a Shakedex "bid".

Protocol facts behind this spec, pinned to hsd v8.0.0, shakedex `2c4fa04eab68a528e758598d11b5da5666113b11` and learnhns-market `3d117361166c806e587752f56b44b9ab13abefc3`, are in the internal knowledge base (`.mimocode/research/shakedex-protocol.md`, not in git). Anything a test depends on is copied into the repository (R1, R2).

## 3. Requirements

Requirements name the code that enforces them and the test that pins them. Those of the selling and clean-up stages name code that does not exist yet (the cancel, the lock keys, selling and publishing). "UI only" marks a requirement whose behaviour lives in the frontend and is pinned by a component test.

### 3.1 Protocol

**R1 — Byte-identical with hsd.** The lock script `OP_TYPE TRANSFER EQUAL IF <pub33> CHECKSIG ELSE OP_TYPE FINALIZE EQUAL ENDIF`, its P2WSH address (program = SHA3-256 of the script), the price-step template, its `0x84` (`ANYONECANPAY|SINGLEREVERSE`) signature, the purchase, the unsigned FINALIZE out of the lock (witness `[lockScript]`) and the `0x83` (`ANYONECANPAY|SINGLE`) cancel are reproduced byte for byte against vectors generated by hsd v8.0.0.
*Enforced:* `noncustodial/shakedex/{script,template,purchase}.rs`, on `noncustodial/tx.rs`; selling adds `noncustodial/shakedex/cancel.rs` and a P2WSH signing path next to `sign_p2wpkh_input`.
*Pinned:* `tests/shakedex_vector_tests.rs`, vectors generated into `src-tauri/tests/vectors/` by an extension of `gen_hsd_vectors.js` (the research vector covers signing price steps and the purchase only; the buyer's FINALIZE is added there, and selling adds the cancel and its FINALIZE).

**R2 — Listing file is Shakedex v2 JSON, read strictly.** Only `version: 2`. Every price step carries a 65-byte low-S signature whose last byte is exactly `0x84` — shakedex accepts any sighash type that verifies, this wallet does not. `feeAddr` with `fee == 0` means no fee output. `expiresAt` is read and shown, never enforced: a listing file writes it in seconds, the Market feed as a naive UTC ISO-8601 string, and both are read; anything else is refused. The name must be a valid Handshake name (`names::verify_name`). Unknown fields are preserved on round-trip and not interpreted. Input over 256 KiB is refused before parsing. A step's lock time must fit R3's 40-bit encoding, and its price plus fee must not exceed the money supply (`MAX_MONEY`). `paymentAddr` must be 20-byte version-0 under this profile's prefix, so a mainnet file cannot be bought from a regtest profile; an unusable `feeAddr` does not refuse the file, it only pays no fee (R11).
*Enforced:* `noncustodial/shakedex/listing_file.rs`.
*Pinned:* `tests/shakedex_listing_file_tests.rs` (including `wrong_sighash_byte_refused`, `high_s_signature_refused_at_import`, `other_network_prefix_refused`, `invalid_name_refused_at_import`, `unencodable_lock_time_or_amount_above_money_supply_refused_at_import`, `live_market_feed_rows_parse_with_their_iso_expiry`, `unreadable_expiry_refused`), live LearnHNS fixtures (`dexreviews`, `cooljobs`) committed under `src-tauri/tests/vectors/shakedex/`, round-trip unchanged.

**R3 — Validity of a price step follows consensus exactly.** A step's lock time is encoded as `0x80000000 | floor(lockTime / 512)` and the step is valid in the next block when `floor(lockTime / 512) * 512 < MTP`, where MTP is the tip's `mediantime` (`getblockchaininfo`) — strictly less, and up to 511 s before the nominal time. The template signs input 0 with sequence `0xfffffffe`; with `0xffffffff` hsd treats the transaction as final regardless of lock time and every future step would be buyable at once. The **current step** is the cheapest step valid by this rule across the original schedule and every Lower price step.
*Enforced:* `noncustodial/shakedex/template.rs::{encode_lock_time, is_valid_at}`, `noncustodial/rpc.rs` (`BlockchainInfo` gains `mediantime`).
*Pinned:* `noncustodial::shakedex::template` unit tests `{boundary_at_mtp, sequence_is_fffffffe}`.

**R4 — Fees are charged on vsize, including foreign witnesses.** The purchase (seller's input witness `[sig65, lockScript]`), the buyer's FINALIZE (`[lockScript]`), the cancel and the cancel's FINALIZE are sized with their real witnesses, not the P2WPKH constants, at the profile's fee rate with a floor of 5000 doos/kB as shakedex uses.
*Enforced:* `noncustodial/shakedex/purchase.rs` (the fee is charged on the vsize of the plan signed in full, foreign witness included, with the floor `SHAKEDEX_MIN_RATE_PER_BYTE`).
*Pinned:* `noncustodial::shakedex::purchase` unit test `fee_covers_hsd_vsize_with_foreign_witness`, and `shakedex_vector_tests::{purchase_plan_matches_hsd_signed_hex, purchase_finalize_plan_matches_hsd_signed_hex}` against hsd-signed transactions.

### 3.2 Buying

**R5 — Two ways in, one way through.** A listing comes from the Market tab (LearnHNS Market, `GET /api/v2/auctions`), a listing file, pasted JSON, or a `market.learnhns.com/listing/<name>` link (fetched as `/listing/<name>/proof.json`). Arbitrary URLs are not fetched, and a link whose file names another name is refused. Every path produces a listing file and goes through R7 and R10.
*Enforced:* `market/learnhns.rs`, `commands/shakedex.rs::shakedex_import_listing`.
*Pinned:* `shakedex_cmd_tests::{import_text_and_file, import_link_fetches_listing_file, import_link_only_learnhns, import_link_refuses_a_file_for_another_name}`, `learnhns_tests::only_learnhns_listing_links` (each source; a non-LearnHNS URL is refused).

**R6 — Buying needs a node that can send.** `LocalNode`, or `RemoteNode` with "Allow sending via remote node" — the existing write capability (`WriteCapability::evaluate`), now also checked when the purchase draft is built, not only at broadcast. Profiles other than recovery-phrase ones (Ledger, watch-only, extended private key) cannot buy (R16).
*Enforced:* `commands/shakedex.rs::software_writer_ctx`, used by `shakedex_build_purchase_draft` and `shakedex_build_purchase_finalize_draft`.
*Pinned:* `shakedex_cmd_tests::build_purchase_refused_without_write_capability`, `shakedex_finalize_tests::finalize_refused_without_write_capability`.

**R7 — Verified locally, on the profile's node.** Before Buy is offered:
- the listing file passes R2;
- the lock script is `lock_script(publicKey)` and SHA3-256 of it equals the lock coin's program;
- the lock coin, fetched with `GET /coin/:hash/:index` (a new REST wrapper — `gettxout` carries no covenant and returns null for a spent coin, the same as for one it does not know), exists, is unspent, carries FINALIZE with `items[2] == name`;
- the lock outpoint is the name's current owner in `getnameinfo`, and the coin's covenant height equals the name's height — otherwise the name expired and was re-registered and the lock coin is a leftover;
- each price step's signature is valid ECDSA over `signature_hash(0, lockScript, coin.value, 0x84)` of the template, with `price > 0`.

A node reply that leaves out a field these checks read (the coin's address or covenant, the covenant's name and height items, the name's `info`, owner, height, renewal or claimed) means the listing could not be checked, never that it failed. What the market says about availability is ignored. A spent or leftover lock coin is not a safety issue — the network would reject the purchase and nothing would be paid — but such listings are not offered.
*Enforced:* `noncustodial/shakedex/verify.rs`, `noncustodial/rpc.rs::get_coin`.
*Pinned:* `shakedex_verify_tests` (tampered price, wrong lock address, spent coin, re-registered name, covenant height mismatch, and every missing field as "could not check": `lock_coin_without_address_or_covenant_could_not_be_checked`, `name_without_owner_could_not_be_checked`, `name_without_height_could_not_be_checked`, `name_reply_without_info_key_could_not_be_checked`, `lock_coin_covenant_without_readable_name_or_height_could_not_be_checked`), and a 404 that is not hsd's empty one is not a spent coin (`rpc::tests::get_coin_404_with_a_body_is_an_error_not_spent`); the sighash byte and the network prefix are refused by R2's parser.

**R8 — What can be bought, and what is hidden.** The Market list shows only listings that pass R7 and R9. Below it: "Hidden N: X already sold or cancelled, Y failed verification, Z expire before they can be finalized, W not valid yet, V could not be checked" (zero parts left out), expandable to names and reasons, without Buy. The list pages through the market a hundred listings at a time (`MarketPage.{page, pageCount}`, from the feed's `total`); the rows and the counter are the page shown. In SPV and Explorer modes, where R7 cannot run, every row is shown as "Not verified — needs a full or remote node" and none has Buy.
*Enforced:* `commands/shakedex.rs::shakedex_list_market`, `src/components/market/MarketPage.tsx`.
*Pinned:* `market-list.test.tsx` (hidden counter, unverified rows in SPV).

**R9 — A name that would expire before it can be finalized cannot be bought.** Only CLAIM, REGISTER, RENEW and FINALIZE restart a name's renewal clock; a purchase (TRANSFER) does not. Using hsd's claim-aware expiry end for the name, if it falls at or before `tip + 1 + transferLockup + 1 day` (in blocks, from the network's parameters; mainnet 288 + 144), the listing cannot be bought: the Market list hides it (R8), an imported listing shows the reason without Buy, and building the purchase refuses it. "1 day" is 144 blocks, or the transfer lockup itself where that is shorter (regtest's 10 blocks, simnet's 5; values from `noncustodial/network.rs`). On regtest, whose renewal window is 5000 blocks, a 144-block day would make the warning window 4320 blocks and warn on most of a name's life; with the lockup as the day it is 300. If it falls within 30 such days after that, Buy stays enabled with a warning that forgetting to finalize loses the name.
*Enforced:* `noncustodial/network.rs::NameParams::expiry_end` (the one expiry rule, also behind Renewals and the name actions), `noncustodial/shakedex/verify.rs::finalize_deadline_ok`.
*Pinned:* `shakedex_verify_tests::{expiring_name_blocked_and_warned_mainnet, expiring_name_regtest_margin_is_relative, name_about_to_expire_is_hidden, name_expiring_within_a_month_is_buyable_with_warning}`, `market-list.test.tsx` (an import that expires before it can be finalized shows why, without Buy).

**R10 — The buyer pays exactly the current step, and sees every line.** The confirmation shows the price to the seller, the market fee (if paid) in HNS and as a percentage of the price in exact hundredths, the network fee and the total, and says the name becomes the buyer's after a finalize, the network's transfer lockup in blocks after the purchase is mined, with its approximate time where miners set the pace (288 blocks, about two days, on mainnet; no time on regtest and simnet, which mine on demand). Both texts come from one place (`purchase::{fee_percent_text, finalize_wait_text}`), so the dialog and the secure window cannot disagree. The secure spend confirmation gets the same rows; its summary is extended for purchases, which must not count the name's own value as money spent. The current step is re-checked against MTP just before broadcast; if it changed, or the node cannot say, the draft is discarded and the user is asked again.
*Enforced:* `commands/tx.rs::confirm_details_for_draft`, `src/components/market/PurchaseConfirm.tsx`.
*Pinned:* `shakedex_cmd_tests::{confirm_rows_for_purchase, confirm_rows_show_the_stored_finalize_wait, broadcast_refused_when_a_cheaper_step_became_valid, broadcast_refused_when_the_paid_step_is_no_longer_valid, broadcast_refused_when_the_recorded_price_is_unreadable}`, `noncustodial::shakedex::purchase` unit tests `{fee_percent_text_is_exact_to_the_hundredth, finalize_wait_text_times_only_networks_with_miners}`, `purchase-confirm.test.tsx`.

**R11 — The market fee is paid only when it is the market's own.** `fee` and `feeAddr` are not covered by the seller's signature, and anyone can upload a copy of a listing to LearnHNS with any fee. The "Pay the market fee" checkbox is on by default only when the listing came from LearnHNS (the renderer says so; it already decides the checkbox, and a fee it calls the market's must still match the market's own address and rate), `feeAddr` equals the address in its `GET /api/v2/fee_info`, and `fee <= floor(rate × price / 10000)` for the rate published there. Otherwise — file or paste, a different address, or a higher fee — it is off, with "not signed by the seller and not the market's published fee — anyone could have added it". A missing or invalid `feeAddr` adds no fee output, and the line says why (upstream Bob 2.1.0 burns such a fee to the all-zero address). A fee below the dust limit adds no output either, for the same reason a relay would refuse it.
*Enforced:* `commands/shakedex.rs::decide_market_fee`, `market/learnhns.rs::{fee_info, market_fee_is_published}`.
*Pinned:* `shakedex_cmd_tests::{published_market_fee_is_paid_when_chosen, foreign_market_fee_is_not_paid_by_default, fee_from_a_file_is_never_published, unusable_fee_address_is_never_paid}`, `learnhns_tests::market_fee_must_match_published` (above the published rate).

**R12 — Reverse auctions are bought at the current step.** The listing shows the current price, the next step and when it becomes valid by R3, the floor, and the full schedule. There is no automatic buying when the price drops.
*Enforced:* `noncustodial/shakedex/template.rs::current_step_index`.
*Pinned:* `noncustodial::shakedex::template` unit test `current_step_is_cheapest_valid`, `market-list.test.tsx` (every step, now / next / floor).

**R13 — A purchase is tracked from the moment it is sent, from the chain.** Before broadcast a `shakedex_purchases` row is written (listing file, txid, our name destination) in the same database transaction as the purchase draft, which reserves our funding outpoints. The name destination is a fresh receive address, and the row marks it used, so the next allocation skips it. A purchase draft never sent is discarded with its row once its coin reservation expires (`RESERVATION_TTL_SECS`, an hour): a broadcast refuses it from then on, and the sync deletes it only after a further send grace (`shakedex_jobs::SEND_GRACE_SECS`), so a send that started before the TTL never loses its row while it talks to the node. State is derived on every sync from what spends the lock coin and from the TRANSFER covenant, not from draft status:
- **Unconfirmed purchase:** our purchase is in the mempool.
- **Awaiting finalize · N blocks:** our purchase is mined and the TRANSFER at the lock address commits (covenant items 2–3) to our name destination; N = `purchase height + transferLockup − (tip + 1)`, because hsd judges the FINALIZE at the next block (`NameParams::blocks_until_finalize`).
- **Lost, nothing paid:** the lock coin is spent by anything else, hsd answered the broadcast with its own JSON-RPC error (in hsd 8.0.0 only for input it cannot parse; a reply that is not hsd's leaves the draft `broadcast_pending`), or the purchase was absent from the node's mempool and chain for 6 blocks, rebroadcast once, and still absent. Where it may not be rebroadcast (the daemon, or a remote node without the opt-in), it waits for a sync that may, but only until hsd's mempool expiry (72 hours, `MEMPOOL_EXPIRY_BLOCKS`) has passed: then it is lost too, its coins released. The rebroadcast re-checks the price like any broadcast (R10): if a cheaper step has become valid, the old price is not sent again and the purchase is lost here; if the paid step is not valid at the median time (it went back in a reorg), hsd would take the purchase as non-final and still answer with its txid, so nothing is sent and it waits like one that may not be rebroadcast; without the node's median time nothing is sent and nothing decided. Activity says nothing was paid. hsd 8.0.0's `sendrawtransaction` answers with the txid whatever its mempool does with the transaction (`rpc.js` relays it without awaiting the result; a purchase of a lock coin already spent is kept as an orphan), so a purchase someone else beat reads as sent and is lost once the job finds it missing with the lock coin spent.
- **Lost, paid:** our purchase is mined but its TRANSFER commits elsewhere, or the name expired (hsd's `"info": null`) or was won again before it was finalized. Activity shows the reason, and never says nothing was paid.

A mined purchase whose TRANSFER is spent on chain is never lost: only our FINALIZE can spend it, since the lock address's script allows a coin to be spent only into a TRANSFER signed by the seller or into a FINALIZE, and hsd never lets a TRANSFER be spent into another TRANSFER. With the name no longer at our destination, it is owned (the name moved on since) once that FINALIZE is found, mined, in our destination's history; no FINALIZE there, or one still in the mempool, gives no verdict. No purchase is declared lost while anything on chain still traces to it, and a node reply that leaves out a field the trace reads (the name's owner, `info`, the owner coin's address, the TRANSFER coin's covenant or its address items) leaves the purchase as it is until a later sync. On lost, our funding coins are released. A purchase lost while paying nothing is checked again for 7 days (hsd forgets a mempool transaction after 72 hours, but another node can still mine it, and a reorg can undo a competing purchase): once its TRANSFER is mined to us it is awaiting finalize again, and once its own transaction is mined and the name has been finalized to our destination since (anyone may send the FINALIZE) it is owned; either way its draft goes back to broadcasted. Until confirmed, the purchase's change is excluded from coin selection. A reorg moves the state back: an owned purchase is looked at again for 7 days, and if its TRANSFER coin is unspent again (the FINALIZE spends it), it is awaiting finalize again. Only our own funding inputs are reserved in `wallet_tx_drafts`; the seller's lock coin is not ours to reserve. The step runs from `run_sync_steps` in the app and in the daemon; only the app's sync rebroadcasts (SECURITY.md).
*Enforced:* migration `033_shakedex.sql` (`shakedex_purchases`), `shakedex_jobs.rs::refresh_purchases_step` run from `run_sync_steps`, `db/queries.rs::insert_tx_draft_reserving_coins_in_tx` with `DraftPlan::own_inputs` (own inputs only), `commands/tx.rs::classify_broadcast_outcome_with_client` (only hsd's own error fails a broadcast), `commands/tx.rs::refresh_tx_confirmations` (only hsd's own "not found" drops, fails or reverts a draft, and a purchase draft is never dropped or failed there: the purchase job gives it up after its rebroadcast).
*Pinned:* `shakedex_purchase_store_tests::destination_address_counts_as_used`, `shakedex_cmd_tests::draft_reserves_only_own_inputs_and_records_purchase`, `tx_lifecycle_tests::{refresh_gives_no_verdict_on_a_reply_that_is_not_hsds, refresh_leaves_an_unseen_purchase_to_the_purchase_job}`, `shakedex_purchase_state_tests` (lost to another buyer, rejected at broadcast, never mined, reorg back to unconfirmed, `daemon_never_rebroadcasts_and_leaves_it_to_the_app`, `name_reply_without_owner_never_loses_a_purchase`, `owner_coin_spent_in_the_mempool_never_loses_a_purchase`, `transfer_coin_without_readable_covenant_never_loses_a_purchase`, `rebroadcast_refused_when_a_cheaper_step_became_valid`, `rebroadcast_waits_when_the_price_cannot_be_rechecked`, `rebroadcast_waits_while_the_paid_step_is_not_valid_yet`, `app_sync_leaves_purchases_alone_on_a_node_still_catching_up`, `owned_purchase_whose_finalize_was_reorged_away_awaits_finalize_again`, `owned_purchase_whose_transfer_stays_spent_stays_owned`, `unpaid_lost_purchase_that_mines_later_awaits_finalize_again`, `unpaid_lost_purchase_finalized_since_is_owned`, `unpaid_lost_purchase_is_not_owned_by_another_purchases_finalize`, `old_or_paid_lost_purchases_are_not_looked_up`), `shakedex_purchase_store_tests::change_of_unconfirmed_purchase_is_not_spendable`, `node_rpc_injected_tests::broadcast_classify_reply_not_from_hsd_marks_pending`, `rpc::tests::only_hsds_own_json_rpc_error_is_a_rejection`.

**R14 — The purchased name is shown, and its finalize is offered.** Owned Names gains a source for purchases: the name appears as "Unconfirmed purchase", then "Awaiting finalize · N blocks", then owned once it arrives at our address. **R15 — Mainnet buying is experimental.** The Market tab is visible to everyone. Building a purchase draft on mainnet requires the setting `shakedex_experimental`, checked in the backend; on testnet and regtest it is always allowed. The flag gates only new purchases and new listings: Finalize, Cancel, Lower price, reminders and background jobs for what already exists keep working whatever it says. *Enforced:* `commands/shakedex.rs` (`shakedex_experimental`, default off).

**R16 — Shakedex from recovery-phrase profiles only, for now.** Ledger, watch-only and extended-private-key profiles have Buy and Sell disabled with "Shakedex works with a recovery-phrase wallet for now". An extended-private-key profile signs in software too, but its signing of a plan with a foreign input is not verified yet, so it is held back with the others. ### 3.3 Selling

**R17 — Lock keys come from the seed.** One per name and account: `m/44'/<coin type>'/<account>'/2'/<i>'`, `i = u32_be(nameHash[0..4]) & 0x7fffffff` (nameHash = SHA3-256 of the name), every level hardened (ADR 0004). The wallet never sends coins to a lock address and signs only price steps and cancels with a lock key; coins someone else sends there are not counted as spendable. Golden vector (test phrase of `gen_hsd_vectors.js`, account 0, name `dexreviews`, nameHash `55731c3d…40b5c1`, i = 1433607229):

| Network | Path | Lock address |
|---|---|---|
| main | `m/44'/5353'/0'/2'/1433607229'` | `hs1qkq6yytu0c4puw0xlrdwedylkk5a04yrgecgz9wgyu2sua3mzh4jqt74rdj` |
| regtest | `m/44'/5355'/0'/2'/1433607229'` | `rs1qr3mxw2n44nxqf43jqr69d42nmypn84jgzxtxeafpxn4nq58tylzsrz9ec5` |

*Enforced:* `noncustodial/shakedex/lock_key.rs` on `ExtendedPrivKey::derive_path`.
*Pinned:* `shakedex_lock_key_tests::golden_path`.

**R18 — The lock is checked before the name enters it.** A wrong key or script would strand the name: FINALIZE into the lock needs no signature, but every way out does. Before broadcasting the day-0 TRANSFER, the wallet derives the lock key, builds the script and address, signs a test `0x84` over a template and verifies it. Before the FINALIZE into the lock, it re-derives and checks that the confirmed TRANSFER's covenant commits to SHA3-256 of `lock_script(derived pub)`. Either check failing refuses the step.
*Enforced:* `commands/shakedex.rs::{build_lock_draft, build_lock_finalize_and_sign}`.
*Pinned:* `shakedex_sell_tests::{refuses_lock_on_self_check_failure, refuses_finalize_on_commitment_mismatch}`.

**R19 — Selling is two clicks around the transfer lockup.** Day 0: choose Buy Now or Reverse auction, the price or schedule, and "Publish on LearnHNS Market" (on by default); the dialog states R27's costs; Lock name builds a TRANSFER committing to the lock address (it stays at the seller's own address until finalized) and needs the unlocked signer. Between day 0 and the FINALIZE the abort is the existing Cancel transfer (an UPDATE); it also withdraws the pending listing. After the lockup a notification, repeated daily until acted on; Finalize & sign prices builds the FINALIZE to the lock and signs every price step in one unlock, with a last chance to change the price. The listing is published once that FINALIZE has one confirmation. A Buy Now's lock time is the MTP at signing minus 512 s, so it is valid at once by R3.
*Enforced:* `commands/shakedex.rs`, a lock-targeting finalize (the generic finalize accepts only P2WPKH targets), `address` encoding for 32-byte programs, `commands/deadlines.rs` (new kind `listing_ready`).
*Pinned:* `shakedex_sell_tests::{lock_then_finalize_and_sign, buy_now_valid_immediately}`, `deadlines_tests::listing_ready_repeats`.

**R20 — The signer shows everything it is about to make permanent.** The combined Finalize & sign confirmation (a new secure prompt, not the transaction one) lists the FINALIZE's fee and every step's price and the time it becomes valid, and says each signature lets anyone buy at that price until the listing is cancelled and the cancel is mined.
*Enforced:* `commands/shakedex.rs::build_lock_finalize_and_sign` via `prompt_secure`.
*Pinned:* `shakedex_sell_tests::confirmation_lists_every_step`.

**R21 — Proceeds go to a fresh address, reserved.** Each listing pays a receive address that is marked used when the listing is created, so the next listing gets another one and a restore's gap-limit scan still reaches it. The cancel destination is reserved the same way (a buyer's name destination already is, R13).
*Enforced:* `noncustodial/derivation.rs` (reserve on allocation).
*Pinned:* `derivation_tests::reserved_addresses_are_not_reissued`.

**R22 — Sold means the lock coin was bought.** A listing is Sold when its lock coin is spent by a TRANSFER that commits to an address not ours, in a transaction whose payment output pays our listing address. Coins arriving at the payment address on their own mean nothing.
*Enforced:* `shakedex_jobs.rs::refresh_listings` from `run_sync_steps`.
*Pinned:* `shakedex_sell_tests::{sold_on_purchase, payment_alone_is_not_sold}`.

**R23 — Publishing.** With the box ticked and a mainnet profile only: a pending listing on day 0 (`POST /api/v2/pending-listings`), then the active listing after R19 (`POST /api/upload-proof`, multipart field `proof`). LearnHNS accepts one price step per upload and `lockTime <= now + 2 h`. We write `expiresAt = MTP + 365 days` and refresh it before it lapses. The listing file is always saved and can be exported whatever the box says. The help text says publishing makes the name, price and lock public, and that the market sees our IP on every check.
*Enforced:* `market/learnhns.rs` (refuses any write unless the profile network is main), `shakedex_jobs.rs`.
*Pinned:* `learnhns_tests::{no_http_off_mainnet, upload_shape}`.

**R24 — Reverse auctions on a market that sells one price.** All steps (2 to 1000, at least 15 minutes apart) are signed at once and the listing file carries them all. LearnHNS gets the current step (R3) as a single-step upload, replaced as the schedule moves. A future step leaking early is harmless because of R3's lock time and sequence.
*Enforced:* `shakedex_jobs.rs::advance_reverse_auctions`.
*Pinned:* `shakedex_jobs_tests::uploads_current_step_only`.

**R25 — Keeping our listing on the market.** About hourly, `GET /listing/<name>/proof.json` is compared with the current step: re-upload unless it matches it semantically (same lock, key, payment address, price, lock time, signature). The listing's status says "replaced on the market by someone else's copy — re-uploaded" or "Not on market — retrying" (exponential backoff). These jobs need no keys; they run from `run_sync_steps` in the daemon and in the app (the daemon's "read-only" contract is updated to "never signs or broadcasts"). Uploads are unauthenticated, so this is the only defence against replacement.
*Enforced:* `shakedex_jobs.rs::keep_listed`.
*Pinned:* `shakedex_jobs_tests::{reuploads_when_replaced, backs_off_when_unreachable}`.

**R26 — Lower price is instant; raising needs a cancel.** Lower price needs the unlocked signer, checks on the node that the lock coin is unspent and is this listing's, requires a price below the current step, and signs one new step valid now (R19's lock-time rule). For a reverse auction, dearer steps become moot and the schedule continues below the new price. Disabled while a cancel is unconfirmed. Raising is impossible: an earlier signature stays valid until the lock coin is spent.
*Enforced:* `commands/shakedex.rs::lower_price`.
*Pinned:* `shakedex_sell_tests::{lower_price_becomes_current, lower_refused_during_cancel}`.

**R27 — The seller is told what locking costs.** In the Lock dialog: once finalized into the lock, the name's DNS records cannot be changed and it cannot be renewed (the lock script allows only TRANSFER and FINALIZE out), and the listing lasts at most until the name expires — `renewalWindow` after the FINALIZE into the lock (mainnet about two years). While a name is locking or locked, UPDATE, RENEW, TRANSFER, Finalize and batch actions on it are not offered; the new owner-spend actions join `owner_spend_in_flight`.
*Enforced:* `src/components/market/LockDialog.tsx`, `commands/names.rs` capability gates.
*Pinned:* `names_cmd_tests::locked_name_offers_no_owner_actions`.

**R28 — Cancel.** Needs the unlocked signer. The lock key signs a `0x83` TRANSFER at the lock address committing to a reserved address of ours (R21); after the lockup a FINALIZE (notification, button, R14's pattern) brings the name home. The dialog says that until the cancel is mined a buyer can still take the current price, and that if a purchase is already in our node's mempool, the cancel is not taken and never mined, though hsd still answers it with its txid. Once a cancel is broadcast, R24 and R25 stop for that listing and the market is told (`POST /api/v2/listings/<name>/refresh-status`). If a purchase wins, the cancel's reserved coins are released and the listing is Sold.
*Enforced:* `noncustodial/shakedex/cancel.rs`, `commands/shakedex.rs::cancel_listing`.
*Pinned:* golden-vector cancel (R1), `shakedex_sell_tests::{cancel_stops_jobs, purchase_beats_cancel}`.

**R29 — Selling follows the buying gates.** Software profiles only (R16), the same experimental flag on mainnet (R15), and on testnet and regtest listings are shared as files only (R23).

### 3.4 Interoperability

**R30 — A Namehold listing is buyable elsewhere, and the reverse.** On regtest: the shakedex CLI (`shadstoneofficial/shakedex` at a pinned SHA) creates a listing and Namehold buys it (buying); Namehold creates one and the shakedex CLI buys it (selling). Manual, not in CI: it needs an hsd wallet, which `scripts/regtest.sh` disables today, so the harness gains a wallet-enabled mode. The same harness meets the CLI as the other party for the buying stage's chain paths: it buys a listing first, cancels one, and lists a reverse auction, and the node's blocks are taken away under a purchase and its FINALIZE.
*Enforced:* `scripts/regtest.sh --with-wallet`, `scripts/shakedex-cli-sell.sh` (`fixed`, `auction`, `cancel`, `fill`).
*Pinned:* `tests/live_node_it.rs::{shakedex_cli_listing_is_bought, shakedex_cli_buyer_first_loses_ours_with_nothing_paid, shakedex_purchase_follows_reorgs_of_its_own_blocks, shakedex_reverse_auction_pays_the_current_step_and_refuses_a_stale_one, shakedex_cancelled_listing_is_not_offered}` (env-gated: `HNS_IT_NODE_URL` and `HNS_IT_SHAKEDEX=1`).

## 4. Explicitly not enforced

- Nothing stops a seller and buyer agreeing a price elsewhere and using a plain Transfer and Finalize. That still works and needs none of this.
- `expiresAt` does not end a listing. Only a mined cancel does; the wallet says so wherever an expiry is shown.
- The market is not trusted for availability, fees or expiry, and is not needed for safety. Taking a listing off LearnHNS does not stop anyone holding the listing file from buying, at any step that is still valid — including a dearer one than the current step.
- A purchase is not protected against another buyer taking the same listing first. The loser pays nothing.
- No automatic purchase when a reverse auction reaches a price.
- ADR 0003's "no `hns-swap` dependency" is checked by a test that fails if `Cargo.lock` contains it.

## 5. Known gaps

- **Ledger, watch-only and extended-private-key profiles.** No buying or selling (R16, R29).
- **Background jobs need a running process.** Republishing, stepping reverse auctions and finalize reminders run while the app or `namehold-syncd` runs; reminders run only in the app. The listing file keeps working regardless.
- **Recovery of a lock needs new discovery.** After a restore the wallet finds its locks by deriving lock addresses from names in its own address history (ADR 0004). Today's sync does not read address history on the node path and caps it on the explorer path, and explorers exist only on mainnet, so selling adds a history scan; a remote node without `--index-tx` cannot do it.
- **A restored lock has no listing details.** Price steps, schedule and payment address are off-chain. A restored lock shows "Locked — listing details unknown: import its listing file, or cancel"; the saved listing file is the backup.
- **One device per listing.** Devices or profiles sharing a seed derive the same lock keys but not the same listing state; their background jobs would fight over uploads, and one device's Lower price is invisible to the other.
- **A node without a transaction index sees less.** The app's own hsd runs with `--index-tx`; a remote node may not. Without it hsd does not find a mined purchase, so the purchase is followed through its TRANSFER coin and the name's owner instead. A purchase lost while paying nothing and finalized since is shown as owned only once its own transaction is found, which needs the index: on such a node it stays lost, though the name arrives through normal sync.
- **No fee bump.** hsd has no replace-by-fee; an underpaid purchase can only be helped by spending its change (CPFP), which the wallet does not offer.
- **No keep-alive for long listings.** The lock key could restart the renewal clock by transferring the lock coin to itself and finalizing, at the cost of re-signing every step; not offered.
- **Pending listings can be overwritten by anyone** on LearnHNS; only active listings are defended (R25).
- **Shared lock key on a 31-bit hash collision.** Harmless for funds; listing state is keyed by name and outpoint, never by address. It links the two names publicly.
- **One market.** Only LearnHNS Market. Other Shakedex channels, and a censorship-resistant fallback (Nostr relays), are roadmap items.
