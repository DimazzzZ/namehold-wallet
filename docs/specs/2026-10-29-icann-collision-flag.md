# ICANN collision flag

**Status:** implemented (2026-10-29, branch `feat/icann-collision-flag`). Roadmap item P2.13.

## 1. Summary

A Handshake TLD that someone has also applied for as a new gTLD in ICANN's 2026 round is marked wherever the wallet shows the name: a warning badge on every row of the Names page (owned names, auctions, purchases, watchlist), the same badge in the header of the name's page, a row in Details that names the applicants and links to their applications on ICANN's site, and a filter on the Names page that shows only such names. The list of applied-for strings is a file shipped with the app and refreshed by a script; the app never asks ICANN anything at run time.

Why: ICANN published 1,615 applications on 2026-10-07 and will confirm the final list on String Confirmation Day, 2026-11-17. If ICANN delegates one of those strings, resolvers that use the ICANN root answer for it, not for the Handshake name. Someone holding, bidding on or watching such a name should learn that before spending more on it.

## 2. Terms

- **ICANN 2026 round** — ICANN's New gTLD Program: 2026 Round. Applications are published on the Application Publication site, `https://newgtldprogram-aps.icann.org/applications`, whose backend answers `POST https://newgtldprogram-aps.icann.org/aps/applications/export/csv` with a CSV of every application (2,783 rows on 2026-10-29) and `GET https://newgtldprogram.icann.org/en/application-rounds/round2/reveal-day-contention-sets.csv` with the Reveal Day contention sets.
- **Application** — one row of that export: an application id (`AA2634T-T39423`), an applicant name, a primary string, optional variant strings, a status (`Active` or `Deactivated`), a type (`New gTLD`, `Replacement String`, `Existing gTLD with Variants`, `New gTLD with Variants`).
- **Active application** — an application whose status is `Active`. A `Deactivated` application never counts.
- **Replacement** — during the Replacement Period (2026-10-08 to 2026-10-21) an applicant could switch its primary string to another one. The export shows that as a second row whose id is the original id plus `-R` (`IRI2679T-T60293` applied for `consult`, `IRI2679T-T60293-R` for `account`), type `Replacement String`. When the `-R` row is active, the applicant switched: the original row stays `Active` in the export but its string is no longer applied for by that applicant. When the `-R` row is `Deactivated`, the switch was abandoned and the original stands. On 2026-10-29: 1,614 original ids are active, 442 of them have an active replacement, and counting only the string each applicant ends on gives 1,614 applications on 1,203 strings, which matches ICANN's own count (1,615 on publication day). Counting both rows would add 169 strings nobody applies for any more (`action`, `active`, `add`, `any`, `archive`, …).
- **Applied-for string** — the string an active application ends on: its replacement's primary string when it has an active replacement, its own primary string otherwise; plus the variant strings of that row. All as A-labels (`agent`, `xn--3ds443g`). The export gives A-labels in `Primary String`, `TLD Variants` as `<a-label> (<unicode>)` one per cell, and the Unicode form in `Primary String Unicode Label`.
- **Strings list** — `src/data/icann-gtld-2026.json`, generated by `scripts/fetch-icann-strings.ts` (rules and parsing in `scripts/icann-strings.ts`), committed. The only source of applied-for strings the app knows.
- **Collision** — a Handshake name whose ACE form, lowercased, equals an applied-for string of at least one active application. The decoded display form of an IDN name is never compared; Handshake stores IDN names as A-labels, and so does the export.
- **Collision badge** — the warning badge reading `ICANN` that marks a colliding name.
- **In contention** — an application whose string is in a Reveal Day contention set (more than one active application for the same string). Shown in the tooltip and Details only; it does not change what a collision is.

## 3. Requirements

Every requirement names the code that will enforce it and the test that will pin it. `scripts/check-spec-refs.sh docs/specs/2026-10-29-icann-collision-flag.md 1 10` checks every name once the code exists.

### 3.1 The strings list

**R1 — The list is a committed file produced by a script, and nothing in the app reads ICANN at run time.** `scripts/fetch-icann-strings.ts` downloads the export and the contention sets, keeps active applications only, drops an original row whose `-R` replacement is active (Terms: Replacement), and writes `src/data/icann-gtld-2026.json`: `{ "round": "2026", "fetchedAt": "<ISO date>", "source": { "applications": "<url>", "contentionSets": "<url>" }, "strings": { "<a-label>": { "uLabel"?: "<unicode>", "variantOf"?: "<primary a-label>", "applications": [ { "id": "<application id>", "applicant": "<name>", "contention": <bool> } ] } } }`. Keys are lowercase A-labels, sorted; a variant string is its own key with `variantOf` naming the primary string and the same applications; a string with no active application is absent. The script has no dependencies beyond Node, prints the counts it wrote (applications, strings, variants, in contention) and fails loudly when the export's preamble or header changes or when the counts it would write differ from ICANN's published count by more than a handful (a guard against a changed export format, not a hard equality: the published figure moves with withdrawals). `just icann-strings` runs it. The app imports the JSON statically.
*Enforced:* `scripts/fetch-icann-strings.ts`, `scripts/icann-strings.ts::{parseApplicationsCsv, parseContentionCsv, buildStringsList}`, `justfile`.
*Pinned:* `icann-fetch.test.ts` (the parser on a fixture CSV with the two preamble lines; an original with an active `-R` replacement, so the original string is absent and the replacement string carries the `-R` id; an original with a deactivated `-R`, so the original stands and the `-R` is absent; a variant cell `xn--uirx50m (錢包)` that becomes its own key; an IDN with its Unicode label; a contention row; counts match), `icann-list.test.ts` (the committed file is well formed: every key lowercase ACE and sorted, every application has an id and an applicant, `fetchedAt` parses).

**R2 — A collision is an exact match of the lowercased ACE name against the list.** `icannCollision(name)` returns `{ string, uLabel?, applications }` for a colliding name and `null` otherwise. It never decodes punycode and never touches the network; it is synchronous and cheap enough to run for every row on every render.
*Enforced:* `src/lib/icann.ts::icannCollision`.
*Pinned:* `icann.test.ts` (`agent` collides; `Agent` collides after lowercasing; `xn--3ds443g` collides and carries its Unicode label; the decoded form `在线` does not collide; `zzzz-not-applied` does not; a variant key resolves to its primary's applications).

### 3.2 Where the flag shows

**R3 — Every Names row carries its collision, whatever its kind.** `NameRow.icann` is set in the one place every row passes through (`withWatch` in `nameRows.ts`), so owned names, auction positions, purchases and watch-only rows all carry it.
*Enforced:* `src/lib/nameRows.ts::withWatch`.
*Pinned:* `nameRows.test.ts` (an owned name, an auction position and a watch-only name that collide carry `icann`; a non-colliding row carries `null`).

**R4 — A colliding row shows the collision badge in its status cell, unless the row already shows the pending-broadcast badge.** The badge is `Badge variant="warning"` reading `ICANN`, `data-testid="icann-badge"`, with the tooltip "Applied for as a gTLD in ICANN's 2026 round by N applicant(s)" and, when any application is in contention, " · in contention". Design rule: at most one badge per row, by priority; the pending-broadcast badge (a transient state of this wallet's own transaction) wins over the collision badge (a durable property of the name).
*Enforced:* `src/components/NamesView.tsx`.
*Pinned:* `NamesView.test.tsx` (a colliding owned name shows the badge with the applicant count; a colliding row with a pending broadcast shows the pending badge and no `icann-badge`; a non-colliding row shows no badge).

**R5 — The name page header shows the collision badge next to the name.** On `/names/:name` the same badge, with the same tooltip, sits in the H1 line after the name, for any name the page can show, owned or not.
*Enforced:* `src/components/name-page/NameHeader.tsx`.
*Pinned:* `name-page.test.tsx` (the badge is present for `agent` and absent for a non-colliding name).

**R6 — Details has an "ICANN 2026 round" row for a colliding name.** Label `ICANN 2026 round` with a hint tooltip: "Someone applied for this string as a new gTLD. If ICANN delegates it, resolvers that use the ICANN root answer for that TLD, not for this Handshake name." Value: "N application(s)" followed by the applicant names, each a link that opens `https://newgtldprogram-aps.icann.org/applications/<id>/summary` through `openExternal` (the application's own page; `/applications/<id>` redirects there); the first three applicants are named and the rest are "and M more" (the tooltip on it lists them). Sub line: "ICANN list as of <fetchedAt as a date>"; no other date is hard-coded in the copy, so a refresh of the list after String Confirmation Day needs no code change (R10). The row comes first in Details, before "Bought on the market". The Details card renders for a colliding name even when the name has no on-chain record yet (a watched name nobody has opened): then it holds this row and "Nothing on-chain yet." A non-colliding name has no such row, and without on-chain record no card, as today.
*Enforced:* `src/components/name-actions/NameDetails.tsx`.
*Pinned:* `name-details.test.tsx` (the row, its count, three names and "and 2 more" for five applicants, the link target of one applicant, the sub line with the fetched date; the card with only this row for a colliding name without on-chain info; no row for a non-colliding name; no card for a non-colliding name without info).

### 3.3 Finding them all

**R7 — The Filters popover has an "ICANN 2026 round" section with one switch, kept in the URL.** `NameFilters.icann` is `"any"` (default) or `"collision"`; URL param `icann=collision`, omitted when `any`, parsed like the other facets (unknown value falls back to `any`). The popover section shows two pills, `Any` and `Applied for as gTLD`, `data-testid="names-filter-icann-<value>"`. The active-filter pill reads `ICANN collision` and its X resets the facet. `activeFilterCount` counts it. `passesFilters` keeps only colliding rows when set. Chip counts stay over all rows, as for every other facet. Selection is pruned to visible rows as #130 already does.
*Enforced:* `src/lib/nameFilters.ts::{passesFilters, parseNamesParams, namesParams, activeFilterCount}`, `src/components/names/NameFiltersPopover.tsx`, `src/components/NamesView.tsx::activePills`.
*Pinned:* `nameFilters.test.ts` (parse and write round-trip, unknown value, count, `passesFilters`), `NamesView.test.tsx` (setting the switch hides non-colliding rows and shows the pill; the pill's X brings them back).

### 3.4 Copy and freshness

**R8 — The flag states a fact, not a prediction.** Every string of copy says "applied for", never "will be delegated", "taken" or "lost". The consequence sentence in R6 is the only place a consequence is named, and it is conditional on delegation.
*Enforced:* `src/lib/icann.ts::{icannBadgeTitle, ICANN_HINT}`, `src/components/names/NameFiltersPopover.tsx::ICANN_LABELS`.
*Pinned:* `icann-copy.test.tsx` (the badge tooltip, the hint, the filter labels and the rendered Details row against the forbidden words).

**R9 — The user can tell how old the list is.** The `fetchedAt` date is shown in the Details sub line (R6). `docs/RELEASING.md` gets a step: run `just icann-strings` and commit the result before tagging a release; the next mandatory refresh is after 2026-11-17.
*Enforced:* step 3 of docs/RELEASING.md (a document, not code; the reference checker does not look there).
*Pinned:* by review.

**R10 — A refresh that changes the list is a normal PR.** The JSON is committed; a refresh is a commit `chore(icann): refresh the ICANN 2026 strings list (<date>)` whose body gives the counts the script printed. No code changes with it.
*Enforced:* by convention, recorded here.
*Pinned:* none.

## 4. Explicitly not enforced

- No notification, email or Needs you item is raised for a collision; it is a badge, a row and a filter.
- The Market page, listings and Activity rows show no collision badge.
- Nothing is checked against ICANN's existing TLDs; hsd reserves those at the protocol level, and that is a different mechanism.
- The list is not refreshed at run time, on a schedule or on launch. Between refreshes a withdrawn application still counts and a new replacement string does not.
- Strings in contention are not told apart in the badge; only the tooltip and Details mention contention.
- The original string of an applicant who switched to a replacement is not flagged, even though the export still lists that row as `Active` (Terms: Replacement). The applicant no longer applies for it.
- Nothing is done for a name whose decoded (Unicode) form resembles an applied-for string; only the ACE form is compared (R2).

## 5. Known gaps

- **The list changes until 2026-11-17 and after.** Applicants may still switch strings (the Replacement Period ended 2026-10-21) and withdraw (65% refund until 2026-11-27, less later). Accepted: the committed list carries its date (R9) and a refresh is one script run (R10).
- **"In contention" is Reveal Day data.** ICANN's export marks `Label: In Contention` false for everyone until String Evaluation; the script takes contention from the separate Reveal Day CSV, which is a snapshot from before the Replacement Period, keyed by application id and string. The script applies it only where the id and the string still match an application it keeps, so a replaced string does not carry its old contention. Accepted: it is informational only.
- **Existing test fixtures use real applied-for strings.** `nova`, `mine`, `ghost` and `alpha` are active strings, so rows built from those fixtures will carry the badge; tests that count badges or snapshot the status cell need a non-colliding name or must expect it.
- **Only the first three applicants are named inline.** `.agent` has 11 (13 on publication day; two applicants switched to other strings); the tooltip lists the rest.
